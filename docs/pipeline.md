# Visual generation pipeline

`code/main.py` is the entry point that regenerates the visuals embedded in
`writeup/writeup.ipynb`. It runs the full Duel Influence Probability (DIP)
simulation from raw weekly tracking data and writes its outputs straight
into the `writeup/` folder so the writeup notebook always renders against
fresh, reproducible figures.

See [pipeline_flowchart.md](pipeline_flowchart.md) for the diagram.

## Stages

1. **Load and filter** — `dbf.get_all_data()` reads all 18 weeks of
   `data/input_2023_wNN.csv` / `data/output_2023_wNN.csv` plus
   `data/supplementary_data.csv`. `dbf.get_target_plays()` restricts the
   tracking data and `play_info` to man-coverage plays with short routes
   (`SLANT`, `CROSS`, `IN`, `OUT`, `FLAT`).
2. **Enrich play_info** — `dbf.add_to_play_info()` adds the closest
   man-coverage defender (`def_id`), the targeted receiver (`off_id`), and
   the ball release/landing position to each play.
3. **Simulate** — `dbf.get_player_maxes()` derives each player's max
   speed/acceleration directly from the raw tracking data (no cached
   `max_frame.csv` is needed). `dbf.get_all_situation_data()` then runs the
   per-play DIP simulation across every target play, returning
   `all_situations` and `all_probabilities`. This is the most expensive
   stage in the pipeline.
4. **Build analysis features** — the throw-frame (`frame_id == 0`) DIP
   probabilities are merged onto `play_info`, then `dbf.add_player_dir()`,
   `dbf.add_ball_dir()`, `dbf.add_starting_separation()`, and
   `dbf.classify_movement_path()` derive the features used by the summary
   plots (defender movement classification, pass outcome, combined DIP).
5. **Render the two summary PNGs**:
   - `dbf.create_qb_dip_boxplot()` — distribution of offensive DIP at the
     throw, by quarterback (top 10 by play count) → `qb_rep_win_prob.png`.
   - `dbf.create_dip_logistic_fit()` — logistic fit of offensive DIP vs.
     pass outcome, restricted to high-confidence plays
     (`total_bal_prob > 0.90`) with a non-`OUT` defender movement path →
     `off_mwp_log_fit.png`.
6. **Render the three scenario GIFs** — for each play in `SCENARIO_PLAYS`
   (below), `dbf.get_augmented_output()`, `dbf.get_ball_position_frame()`,
   and `dbf.get_animation_data()` rebuild the play's frame-by-frame
   animation data, and `dbf.create_play_gif()` renders the DIP-overlay GIF.

## Configuration (`.env`)

`main.py` reads two variables from a repo-root `.env` (never committed):

- `WRITEUP_DIR` — output folder for regenerated visuals, relative to the
  repo root. Normally `writeup`.
- `SCENARIO_PLAYS` — comma-separated `game_id:play_id` pairs for the GIFs
  to render.

## Running it

```
conda activate data_bowl_2026
python code/main.py
```

## Logging

Every run logs to both the console and a timestamped file in `logs/`
(`pipeline_<YYYYMMDD_HHMMSS>.log`). Rendering each scenario GIF is wrapped
in a try/except — a failure on one scenario play is logged with its
game_id/play_id and skipped, rather than aborting the rest of the run.

## Out of scope

The hand-made full-play GIFs (`cardinals_td.gif`, `houston_fourth_qtr_int.gif`,
`raiders_fourth_down_inc.gif`) and all `.mp4` files in `writeup/` were produced
outside this codebase and are **not** regenerated by `main.py`. If the
underlying DIP logic changes in a way that affects the writeup's narrative
or figures, this document and the writeup notebook should both be revisited.
